## 2. Баги и дыры в архитектуре

- **Админка пользователей падала с 500**: страницы добавления/редактирования (`email`, `bio` — свойства, а не поля модели), поиск по email — `FieldError`. Исправлено кастомными формами.
- Комментарии: API отдавал 10 штук на страницу, фронтенд читал только первую — **комментарии после 10-го не показывались**. Каждый ответ приходил дважды (в списке и внутри родителя).
- Теги и категории были пагинированы по 10 — селектор тегов и фильтры видели только первые 10.
- `create`/`update`/`publish`/`archive` поста возвращали неполные данные (без автора и счётчиков) — фронтенд подменял ими пост в списках.
- `PATCH {status: "published"}` без поля `content` всегда падал с «содержание < 10 символов».
- Файлы не удалялись: старая обложка/аватар при замене, файлы при удалении поста/медиа/пользователя (каскад). Теперь через сигналы `post_delete` + `on_commit`.
- `PUT` медиафайла оставлял старый файл и не пересчитывал тип/размер — замена отключена.
- Тесты писали сотни файлов в реальную папку `backend/media/` (отсюда 66 МБ мусора в архиве) — теперь временная папка.
- `.gitignore` игнорировал `package-lock.json`, хотя CI использует `npm ci` — CI бы падал на чистом клоне.
- Фронтенд: при ротации refresh-токена новый токен не сохранялся; параллельные 401 запускали несколько refresh одновременно → случайные разлогины. Теперь single-flight refresh.
- Фронтенд: класс `.input` использовался во всех select/textarea, но **нигде не был объявлен** — поля были нестилизованными.
- Фронтенд: `http://127.0.0.1:8000` захардкожен в 3 компонентах — в production обложки не загружались. Общий `resolveMediaUrl`.
- Фронтенд: фильтр «Черновики/Архив» в «Моих постах» работал только по текущей странице. Теперь фильтрация на сервере.
- Фронтенд: `MainLayout` содержал полную копию Header и Footer (~200 строк), формы создания/редактирования поста — почти полные копии друг друга. Вынесено в общие компоненты.
- Фронтенд: на странице поста на долю секунды мигало «Пост не найден»; ответ устаревшего запроса мог перезаписать свежие данные (гонка при быстром переключении фильтров).
- Фронтенд: на странице поста нельзя было поставить лайк; крестик на текущей обложке в редактировании ничего не делал.

## 3. Оптимизация

**Бэкенд**
- Лента: было ~3 доп. запроса на каждого автора (N+1 из-за `is_subscribed` и двух `count()`); теперь **константное число запросов** (≤ 4 на страницу независимо от размера) — проверено тестом.
- Счётчики лайков/комментариев: `Count` по двум JOIN давал декартово произведение строк — заменено на коррелированные подзапросы.
- Детальный пост больше не встраивает 50 комментариев с N+1 (фронтенд всё равно грузит их отдельно).
- Список постов не тянет поле `content` (`defer`).
- Дублирующийся поиск (`SearchFilter` + свой фильтр `search`) — три `ILIKE '%…%'` выполнялись дважды.
- Статистика медиа: один агрегирующий запрос вместо загрузки всех строк в Python + 5 `COUNT`.
- Профиль: счётчики подписок и флаг подписки — аннотации, 1 запрос.
- Индексы: составные `(status, -created_at)`, `(author, -created_at)`, `(post, created_at)`, `(user, -created_at)`; удалён лишний индекс на `slug` (уже `unique`).
- `CONN_MAX_AGE` — переиспользование соединений с БД.

**Фронтенд**
- Селекторы zustand вместо подписки на весь стор: любое изменение стора больше не перерисовывает все карточки.
- Оптимистичные лайки с откатом при ошибке и защитой от двойного клика.
- Кеш справочников (теги/категории) на 5 минут вместо запроса на каждой странице.
- Главный чанк приложения: **231 КБ → 32 КБ** (React DOM раньше попадал в него и инвалидировался при каждом деплое).
- `URL.createObjectURL` вместо base64 для превью, `loading="lazy"`/`decoding="async"` у изображений, прогресс чтения без ре-рендеров.
- ErrorBoundary: при ошибке загрузки чанка после деплоя — экран с кнопкой «Обновить» вместо белой страницы.

## 5. Что сделать при обновлении

1. Бэкап БД.
2. `pip install -r requirements.txt`
3. Если использовался ключ из старого `.env.example`: новый ключ в `FIELD_ENCRYPTION_KEY`, затем
   `python manage.py migrate` и `python manage.py rotate_field_key --old-key <старый>`. Иначе просто `migrate`.
4. Фронтенд: `npm ci`. После деплоя пользователям придётся войти заново только если их refresh-токен истёк.

## 6. Рекомендации (не реализовано — требует решения по архитектуре)

- Хранить refresh-токен в httpOnly-cookie вместо localStorage (защита от кражи при XSS).
- Отдавать `/media/` с отдельного домена или через nginx с `Content-Disposition`/CSP.
- В production — Redis вместо LocMemCache (лимиты запросов сейчас считаются на каждый процесс gunicorn отдельно).
- Удалить тестовый мусор из `backend/media/` (сотни `file14_xxx.png` от прошлых прогонов тестов) — оставлен, чтобы не удалить случайно реальные файлы.
